The problem

A wrong number becomes a wrong price

When a contract’s price is tied to a usage metric, the number a rep puts on the quote has to match the source of truth in the data warehouse. In practice they drift — a quote built two months ago, a warehouse key that changed after a rebrand, an account split across three regions, a pipeline glitch that inflates a figure fifty-fold. Each mismatch quietly turns into a mispriced deal, caught late in rework or an awkward renewal.

This tool sits at the moment of the quote: one check returns a reconciled number, a confidence level, and a clear next action — before anything reaches a contract.

The core decision

The number is code. The AI only speaks.

Pointing a language model at the data and asking “what’s the number?” is the obvious move and the wrong one — a figure that feeds a price must be reproducible and auditable. So the work is split cleanly, and the money-bearing path never passes through a model.

Deterministic engine

Decides the number

  • Resolves the CRM → warehouse key mapping
  • Sums business units; never averages
  • Checks freshness and week-over-week plausibility
  • Assigns a status and a confidence level
Bounded LLM

Explains the verdict

  • Turns the finished verdict into one plain sentence
  • Cannot change a number, status, or confidence
  • Optional & pluggable — falls back to a template
  • The system is fully correct with no model at all
The gate

Six checks, in an order that protects the price

Quality checks run before the quote comparison — so an untrustworthy value can never reach the “looks like a refresh” branch and be waved through as safe.

1

Ambiguity guard

Two accounts share one warehouse key? Escalate — the count can’t be attributed to either.

2

Key mapping

Join CRM to warehouse (direct, alias, or a conservative heuristic). No match? Hold — never invent a number.

3

Aggregation

Sum every business-unit row for the account into one figure.

4

Freshness

Source older than the threshold? Review — return it, but flagged as unconfirmed.

5

Plausibility

An implausible week-over-week jump? Withhold the value and route to the data team.

6

Compare to the quote

Only now: within tolerance → match; drifted → refresh to the reconciled number.

The result

Half cleared automatically, half correctly held

Run against the synthetic dataset, every dirty case is caught and routed to a human rather than silently mispriced. Only a clean, fresh, unambiguous account at high confidence is auto-usable.

Architecture

Swappable data in, one verdict out, a human where it matters

Two source readers are the only components that change to move from CSVs to real Salesforce and Databricks. Everything downstream is source-agnostic and tested.

What this demonstrates

The capability behind the case study

The scenario is fictional, but the pattern is one most companies running a CRM alongside a data warehouse actually have.

Judgment about where AI belongs

Knowing which parts of a workflow are exact rules and which are genuinely fuzzy — and keeping revenue-bearing logic out of a non-deterministic model.

Reliability-first engineering

Fail-closed behaviour, explicit failure modes, confidence gating, and graceful degradation when a dependency is down.

Data reconciliation & quality

Messy joins, key drift, stale data, and anomaly detection surfaced and routed — turning bad pricing data into tickets as a side effect.

Verifiable delivery

A hand-labelled eval set, versioned prompts, and unit tests — so “it works” is a claim backed by a check, not a hope.
